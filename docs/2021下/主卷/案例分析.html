案例一：集团信息系统升级（WBS与范围管理）

问题1（12分）

查看参考答案

（1）WBS分解中存在的问题：

  1. 将"数据可视化分析预测功能"模块外包，但在WBS中未包含外包管理工作（供应商管理、外包成果验收等），WBS不完整。
  2. 未经客户确认，擅自增加"软件界面重新设计"工作，将范围外工作纳入WBS，违反了以批准的范围说明书为基础的原则。
  3. WBS分解时，仅由项目经理一人完成，未与相关干系人共同制定，可能遗漏必要工作。
  4. 未对各子公司的数据上报字段和业务需求进行深入调研，导致分解出的工作与实际需求不符。

（2）WBS分解注意事项：

  1. WBS应以项目范围说明书为依据，包含且仅包含批准的项目工作，避免镀金和遗漏。
  2. WBS的最低层应为工作包（可以被分配和管理的最小单元）。
  3. WBS应涵盖项目管理工作本身，不只是技术工作（如项目管理、外包管理等）。
  4. WBS分解应满足"100%规则"：所有子节点工作量之和等于父节点。
  5. WBS应由项目团队共同参与制定，并经过关键干系人评审确认。
  6. WBS的层次不宜过多也不宜过少，一般以3-6层为宜。

问题2（8分）：范围管理中的其他问题

查看参考答案
  1. 需求收集不充分：各子公司数据上报字段与实际业务不符，说明未对子公司进行充分的需求调研。
  2. 范围未经正式确认：没有通过正式的范围确认（验收可交付成果）程序，导致双方对范围的理解存在偏差。
  3. 镀金（Gold Plating）：在客户未提出修改界面需求的情况下，擅自更改UI，属于超范围工作。
  4. 外包模块需求不明确：外包模块的功能边界和接口要求未在范围内明确定义，可能导致交付成果不符合要求。
  5. 缺少变更控制：界面更改属于范围变更，应走变更管理流程，而非直接执行。

问题3（3分）：项目范围说明书的内容

查看参考答案
  1. 产品范围描述（产品特性和功能的逐步精细化描述）
  2. 可交付成果（项目预期产生的所有工作成果及辅助成果）
  3. 项目除外责任（明确不属于项目范围的内容）
  4. 项目制约因素
  5. 项目假设条件
  6. 批准的项目变更（如有）

问题4（9分）：第2个月月底的执行绩效

查看参考答案

按公开参考答案，第2个月月底应从项目整体累计执行情况和财政资金使用情况两部分作答。

（1）项目整体累计绩效：

指标 数值 计算
PV 1100 万元 400 + 700
AC 900 万元 200 + 700
EV 1100 万元 按表3累计完成情况折算

$$SV = EV - PV = 1100 - 1100 = \mathbf{0 \text{万元}}$$

$$CV = EV - AC = 1100 - 900 = \mathbf{200 \text{万元}}$$

$$SPI = \frac{EV}{PV} = \frac{1100}{1100} = \mathbf{1}$$

$$CPI = \frac{EV}{AC} = \frac{1100}{900} \approx \mathbf{1.22}$$

结论：项目整体进度正常，成本节约。

（2）财政资金使用情况：

  • 财政资金按计划应支出 500 万元，实际支出 100 万元，说明财政资金节约。
  • 自筹资金按计划应使用 600 万元，实际执行 800 万元，说明自筹资金超额支出。

案例三：医院信息系统配置管理与质量审计

问题1（10分）：配置管理方面的问题

查看参考答案
  1. 质量工程师小杨兼任配置管理员，角色冲突，不符合职责分离原则。
  2. 将全部配置权限开放给项目经理小王，权限管理混乱，不符合最小权限原则。
  3. 配置变更由小杨直接决定批准，未建立变更控制委员会（CCB）和变更审批流程，变更决策程序不规范。
  4. 配置项修改后版本号未更新（未升版），违反版本管理规范。
  5. 修改后删除了旧代码，违反了配置管理中保留历史版本的原则，无法进行版本回退。
  6. 修改人员在修改前未通过正式的配置变更申请和审批流程，直接检出、修改、检入，缺少审批环节。

问题2（8分）：配置库变更控制流程

查看参考答案
  1. 提出变更申请：需要修改的人员填写配置变更申请单，说明变更原因和内容。
  2. 变更影响分析：配置管理员分析变更对其他配置项和基线的影响。
  3. CCB审批：提交配置控制委员会（CCB）审查，批准或拒绝变更。
  4. 建立新基线（检出）：获批后，从受控库中检出（Checkout）待修改的配置项，在开发库中进行修改。
  5. 执行修改：按照批准方案进行修改，并完成相应测试验证。
  6. 检入并升版：修改完成后，生成新版本号，将修改后的配置项检入（Checkin）受控库。
  7. 通知相关人员：将变更情况通知受影响的干系人。
  8. 保留历史版本：旧版本应保留存档，不得删除。

问题3（5分）：质量审计的目标

查看参考答案
  1. 识别项目中正在实施的所有良好或最佳实践。
  2. 识别所有与政策、流程和程序不符合的差距、缺陷。
  3. 分享同类项目中已证实的良好实践。
  4. 积极、主动地提供协助改进过程执行效果。
  5. 强调每次审计都应对其后形成的、已完成任务的知识库做出贡献。
  6. 确保项目工作符合组织和项目的质量标准及相关规定。

问题4（2分）：选择题

查看参考答案

答案：C（受控库代码的Check权限）

质量管理人员负责检验产品，通常不应具备受控库代码的Check（提交/修改）权限，以保证质量审查的客观性和独立性——受控库是开发人员修改配置项的核心库，质量管理人员不应具备直接修改受控库代码的权限。

注：信管网公开参考答案为C。质量管理人员应具备产品库的各项Read权限以查阅基线内容，但不应具备受控库代码的Check权限以避免"既当运动员又当裁判员"。
