## 案例一：智慧社区APP项目（范围确认与变更管理）

### 问题1（10分）

**（1）7月范围确认会存在哪些遗漏？**

范围确认（核实范围）的主要工作是：检验可交付成果是否满足验收标准，获得客户对已完成可交付成果的正式认可。

本案例7月会议仅讨论了：文档交付物清单、里程碑、工作进度和人员分工图表。

**遗漏的内容：**
1. **未对已完成的可交付成果进行检查和演示**（核实范围应以实物成果为对象，而非计划文档）。
2. **未对功能需求说明书进行正式评审和确认**（客户对需求的正式认可）。
3. **未包含安全性和性能要求的验收标准**（合同要求客户方对安全性和性能有高要求，但未纳入确认内容）。
4. **缺少对验收标准的正式确定和双方签字确认**（虽有会议纪要，但未明确功能和性能的验收条件）。
5. **未识别和确认合同变更**（APP是免费附加，功能范围不明确，应在此时明确）。

**（2）范围确认与质量控制的区别：**

| 对比维度 | 范围确认（核实范围） | 质量控制 |
|---------|-----------------|---------|
| **目的** | 获得客户对可交付成果的正式验收 | 监控和记录质量活动执行结果，评估绩效 |
| **时机** | 项目阶段末或里程碑节点 | 贯穿整个项目执行过程 |
| **执行方** | 客户/发起人（外部） | 项目团队（内部） |
| **关注点** | 可交付成果是否符合范围定义（验收条件） | 可交付成果是否满足质量标准（质量指标） |
| **输入** | 核实的可交付成果（经质控后） | 项目测量结果、质量计划 |
| **输出** | 已验收的可交付成果、变更请求 | 已核实的可交付成果、质量控制测量结果 |

### 问题3（4分）：变更的决策机构

**决策机构：变更控制委员会（CCB）**

**成员组成：**
- 项目发起人或高层管理者
- 项目经理
- 关键客户代表
- 技术负责人
- 财务/合同代表
- 相关领域专家（如安全专家、法律顾问）

**职责：**
1. 评审变更申请，进行独立、客观的变更影响分析。
2. 批准、拒绝或推迟变更请求。
3. 确保变更符合项目目标和合同要求。
4. 监督变更实施情况，跟踪变更结果。

---

### 问题4（6分）：项目变更应开展哪些工作

1. **提出变更申请**：相关方正式填写变更申请单，描述变更内容和理由。
2. **变更影响评估**：分析变更对项目范围、进度、成本、质量、资源和风险的影响。
3. **CCB审批**：将变更申请和影响分析提交CCB，由CCB批准、拒绝或修改变更方案。
4. **更新项目管理计划**：变更批准后，更新范围基准、进度基准、成本基准及相关子计划。
5. **实施变更**：按批准的变更方案执行，并分配相应资源。
6. **跟踪与验证**：跟踪变更实施情况，验证变更结果是否符合预期，关闭变更请求并归档。

### 问题1（12分）：PERT计算 + 时标网络图 + 最少人数

**（1）各活动期望工期：**

- A=4 天
- B=15 天
- C=15 天
- D=10 天
- E=16 天
- F=7 天
- G=8 天
- H=15 天
- I=5 天

**时标网络图逻辑关系：**

```text
START → A(4) → B(15) → C(15) → D(10) → E(16)
                                      ├→ F(7) ─┐
                                      └→ G(8) ─┴→ H(15) → I(5) → END
```

按最早开始时间排列：

| 活动 | ES | EF |
|-----|----|----|
| A | 0 | 4 |
| B | 4 | 19 |
| C | 19 | 34 |
| D | 34 | 44 |
| E | 44 | 60 |
| F | 60 | 67 |
| G | 60 | 68 |
| H | 68 | 83 |
| I | 83 | 88 |

**（2）项目实施所需最少人数：**

只有 F 和 G 存在并行，且 H 必须等待二者全部完成，因此 F、G 不能完全串行执行；并行期间资源峰值为：

$$9 + 12 = 21 \text{ 人}$$

所以项目实施需要的**最少人数为 21 人**。

### 问题2（3分）：关键路径和工期

两条主要路径为：

- A-B-C-D-E-F-H-I = 4+15+15+10+16+7+15+5 = **87天**
- A-B-C-D-E-G-H-I = 4+15+15+10+16+8+15+5 = **88天**

因此：

- **关键路径：A-B-C-D-E-G-H-I**
- **总工期：88天**

---

### 问题3（6分）：第70天时的EVM计算

**已知：**
- 第70天：完成总工作量的3/4，花费60万元
- 各活动日工作量相同

总预算 BAC：

$$BAC = 0.6+6.3+10.4+24.7+10.2+5.1+10.6+15.7+3 = 86.6 \text{万元}$$

**PV：**

按计划到第70天时，应完成 A、B、C、D、E、F、G，并且 H 已经进行了 2 天：

$$PV = 0.6+6.3+10.4+24.7+10.2+5.1+10.6+\frac{15.7}{15}\times 2$$

$$PV \approx 69.99 \approx \mathbf{70 \text{万元}}$$

**EV：**

项目实际完成总工作量的 3/4：

$$EV = 86.6 \times \frac{3}{4} = 64.95 \approx \mathbf{65 \text{万元}}$$

**AC：**

$$AC = \mathbf{60 \text{万元}}$$

**偏差：**

$$SV = EV - PV = 65 - 70 = \mathbf{-5 \text{万元}}$$

$$CV = EV - AC = 65 - 60 = \mathbf{5 \text{万元}}$$

---

### 问题4（4分）：绩效评价与措施

绩效指标：

$$SPI = \frac{65}{70} \approx 0.93 < 1$$

$$CPI = \frac{65}{60} \approx 1.08 > 1$$

**绩效判断：**

- **进度落后**（SV<0，SPI<1）
- **成本节省 / 成本绩效较好**（CV>0，CPI>1）

**项目经理可采取的措施：**

1. 分析关键路径上延期的具体原因，重点关注 G、H、I 等关键活动。
2. 对关键路径活动采取**赶工**或**快速跟进**措施，把进度追回来。
3. 优先投入经验更强的人员到关键活动，避免在非关键活动上分散资源。
4. 加强阶段性监控和里程碑检查，及时更新进度计划并向干系人沟通偏差。

## 案例三：养老保险信息系统（风险管理 + PKI）

### 问题1（4分）：风险管理流程中存在的问题

根据标准的风险管理流程（规划→识别→定性→定量→规划应对→实施应对→监控），案例中流程可能存在：

1. 流程中缺少**定量风险分析**步骤（只有定性分析）。
2. 风险管理流程中未包含**风险监控**环节（控制风险），风险管理是一次性的而非持续的。
3. 未包含**风险再评估**机制，项目执行过程中不会持续更新风险登记册。
4. 风险应对措施未经评审，可能存在遗漏或不当的应对策略。

---

### 问题2（10分）：风险应对策略判断

| 风险描述 | 措施 | 应对策略 | 说明 |
|---------|------|---------|------|
| 人员情绪风险 | 调离项目组 | **规避（Avoid）** | 通过改变安排直接消除该风险源 |
| 缺少数据库设计和相关技术储备 | 外包 | **转移（Transfer）** | 将相关风险和责任部分转移给外部供应商 |
| 需要新的数据安全管理技术 | 培训 | **减轻（Mitigate）** | 通过培训提升能力，降低风险发生概率和影响 |
| 非预期事件造成成本增加的风险 | 应急储备 | **接受（Accept）** | 预留储备应对风险，属于主动接受 |
| 审批流程繁琐 | 加强部门沟通，建立协调配合机制 | **减轻（Mitigate）** | 通过改进协同机制降低管理风险影响 |

### 问题3（8分）：PKI双密钥证书生成过程

**双密钥、双证书机制：**
- **签名密钥对（私钥+公钥）**：用于数字签名，证明身份
- **加密密钥对（私钥+公钥）**：用于数据加密，保护隐私

**证书生成过程：**

1. **密钥生成**：用户（或CA代表用户）生成两对密钥：
   - 签名密钥对（由用户生成，私钥不出卡）
   - 加密密钥对（由CA生成并备份）

2. **申请证书**：用户向证书授权机构（CA）提交身份信息和公钥。

3. **身份验证**：注册机构（RA）验证用户身份（实名认证）。

4. **CA签发证书**：
   - CA对签名公钥签发**签名证书**（Signing Certificate）
   - CA对加密公钥签发**加密证书**（Encryption Certificate）

5. **证书分发**：
   - 签名私钥和签名证书存入用户的密钥介质（如USB Key）
   - 加密私钥和加密证书也存入密钥介质，加密私钥同时在CA/KM处备份（密钥托管）

6. **发布至目录服务**：加密公钥证书发布到公开目录中，供他人加密使用。

**密钥使用：**
- 发送方用接收方的加密公钥加密数据，接收方用加密私钥解密。
- 签名方用签名私钥签名，验证方用签名公钥验证。
