## 案例一：燃气系统升级改造项目（范围管理）

### 问题1（8分）：范围管理方面的问题

<details>
<summary>查看参考答案</summary>

1. 需求评审会无法召开时，项目经理未采取有效措施（如调整时间、线上评审等），直接绕过了需求评审环节，需求基准未经确认。
2. 在未完成需求评审、未确认需求基准的情况下，就直接进入设计和编码阶段，违反了项目管理程序。
3. 将敏捷开发方法作为跳过需求确认的借口，混淆了敏捷迭代与需求无基准开发的概念。
4. 张工在客户验收阶段口头约定使用公司新产品功能来弥补需求缺口，口头约定不具备法律效力，未走变更流程，属于变更管理失控。
5. 变更范围时未评估对成本、进度、质量的影响，擅自增加人员和加班，导致延期1个月。
6. 项目上线后仍有问题，说明测试不充分，验收标准不明确，缺少正式的验收测试过程。

</details>

---

### 问题2（6分）：范围说明书的内容和作用

<details>
<summary>查看参考答案</summary>

**内容：**
1. 项目目标（可量化的成功标准）
2. 产品范围描述（产品特性、功能的逐步精细化描述）
3. 项目可交付成果（以及不可交付物）
4. 项目除外责任（明确不包含在范围内的内容）
5. 项目制约因素
6. 项目假设条件
7. 项目批准要求（验收标准）

**作用：**
- 是WBS、进度计划、成本估算的基础
- 明确项目边界，减少范围蔓延
- 作为验收依据
- 指导项目团队理解项目工作

</details>

---

### 问题3（6分）：需求变更的工作内容

<details>
<summary>查看参考答案</summary>

1. **识别和记录变更**：将甲方提出的新需求（UI风格、接口兼容、加密算法）正式记录为变更申请。
2. **变更影响分析**：评估变更对项目范围、进度、成本、质量、资源的影响。
3. **提交CCB审批**：将变更申请和影响分析提交变更控制委员会（CCB）审批，不能口头约定。
4. **更新项目文件**：变更批准后，更新范围说明书、WBS、项目计划、合同文件等相关文档。
5. **实施变更并跟踪**：按批准方案实施，跟踪实施情况，确保变更得以落实。
6. **验证变更完成**：确认变更内容已正确实现后，关闭变更请求，归档变更记录。

</details>

## 案例二：软件开发项目挣值分析（EVM）

### 题面关键数据说明

原题中该题的数据表以图片形式给出，之前本地文件将其直接重写成了文字表，并标注为“来自原题表格”，这一步**不严谨且口径有误**。

按已核对的公开参考答案，本题在检查点（6月30日）的关键数据应收敛为：

- **BAC = 52000 元**
- **PV = 39800 元**
- **AC = 32000 元**
- 各活动挣值（EV）：
  - A：**25000 元**
  - B：**6000 元**
  - C：**5000 元**
  - D：**0 元**
- **总 EV = 36000 元**

---

### 问题1（13分）：计算各活动挣值及项目SV、CV

<details>
<summary>查看参考答案</summary>

**各活动挣值：**

- A活动：$25000 \times 100\% = 25000$ 元
- B活动：$12000 \times 50\% = 6000$ 元
- C活动：$10000 \times 50\% = 5000$ 元
- D活动：$0$ 元

因此：

- **PV（计划价值）= 39800 元**
- **EV（挣值）= 36000 元**
- **AC（实际成本）= 32000 元**

**偏差计算：**

- **SV = EV - PV = 36000 - 39800 = -3800 元**（进度落后）
- **CV = EV - AC = 36000 - 32000 = 4000 元**（成本节约）

**绩效判断：**

- **SV < 0**，说明**进度落后**
- **CV > 0**，说明**成本节约**

若补充绩效指数，则：

- **SPI = 36000 / 39800 ≈ 0.90**
- **CPI = 36000 / 32000 = 1.125**

</details>

---

### 问题2（3分）：快速跟进的不足

<details>
<summary>查看参考答案</summary>

1. 快速跟进将串行活动改为并行，增加了工作的不确定性和返工风险。
2. 并行执行时，如果前序活动的输出发生变化，会导致后续活动的工作成果需要修改，增加成本。
3. 快速跟进通常只适用于可以并行的活动，并非所有活动都适合，应用范围有限。

</details>

---

### 问题3（4分）：完工估算成本（EAC）

<details>
<summary>查看参考答案</summary>

假设当前偏差属于典型偏差（即未来按当前 CPI 进行）：

$$EAC = \frac{BAC}{CPI} = \frac{52000}{36000/32000} = \frac{52000}{1.125} \approx 46222.2 \text{ 元}$$

</details>

---

### 问题4（5分）：PERT概率计算

<details>
<summary>查看参考答案</summary>

C活动工期估算：
- 乐观工期（O）= 14天，最可能工期（M）= 20天，悲观工期（P）= 32天

$$t_e = \frac{O + 4M + P}{6} = \frac{14 + 4 \times 20 + 32}{6} = \frac{126}{6} = 21 \text{ 天}$$

$$\sigma = \frac{P - O}{6} = \frac{32 - 14}{6} = 3 \text{ 天}$$

目标：24天内完成：

$$Z = \frac{T - t_e}{\sigma} = \frac{24 - 21}{3} = 1.0$$

查标准正态分布表：$P(Z \leq 1.0) = \mathbf{84.13\%}$

**结论：项目经理采用资源优化在24天完成C活动的概率约为84.13%。**

</details>

## 案例三：SaaS平台配置管理与测试

### 问题1（5分）：配置管理方面的问题

<details>
<summary>查看参考答案</summary>

1. 产品经理兼任项目经理和配置管理员，职责不分离，存在角色冲突，缺乏独立性。
2. 所有10名人员都拥有管理员权限，权限设置过于宽泛，违反最小权限原则，无法有效控制配置项。
3. 配置库缺少受控库，只有开发库和产品库，结构不完整（应有开发库、受控库、产品库三层）。
4. 产品库内容与实际运行版本存在偏差，版本管理不规范。
5. 小版本只有代码没有文档，文档与代码不同步。
6. 开发人员随手修改代码，未经配置变更控制流程即直接修改，缺乏变更控制意识。

</details>

### 问题2（10分）：系统测试方案

<details>
<summary>查看参考答案</summary>

| 测试要素         | 内容说明 |
|----------------|---------|
| **测试目的**    | 验证3.01版本的各功能模块符合需求规格说明书，发现系统级缺陷，为优化研发流程提供依据 |
| **测试对象**    | 核心产品3.01版本完整系统，包括代码、文档、数据库等 |
| **测试内容**    | 功能测试、性能测试、兼容性测试、安全性测试、回归测试、用户界面测试 |
| **测试过程**    | 制定测试计划→设计测试用例→搭建测试环境→执行测试→记录缺陷→回归测试→出具测试报告 |
| **测试用例设计依据** | 需求规格说明书、产品功能文档、历史版本缺陷库 |
| **测试技术**    | 功能测试采用黑盒测试；代码逻辑采用白盒测试；接口与安全采用灰盒测试 |

</details>

---

### 问题3（6分）：黑盒、白盒、灰盒测试

<details>
<summary>查看参考答案</summary>

| 测试类型 | 含义 | 用途 |
|--------|------|------|
| **黑盒测试** | 不关注内部代码实现，仅通过输入/输出验证功能是否符合需求规格 | 功能验证、用户验收测试、系统测试 |
| **白盒测试** | 基于代码内部结构进行测试，关注代码逻辑路径、分支覆盖 | 单元测试、代码审查、路径测试 |
| **灰盒测试** | 介于黑盒和白盒之间，部分了解内部结构，针对接口、协议等进行测试 | 集成测试、接口测试、性能调优测试 |

</details>
